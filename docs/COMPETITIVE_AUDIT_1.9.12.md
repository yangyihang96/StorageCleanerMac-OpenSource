# StorageCleanerMac 1.9.12 清理软件三轮对比审计

## 审计边界

- 审计日期：2026-08-25。
- 本机对标软件：CleanMyMac 5.5.7、Mac Sai 1.18.8、Mac Optimizer 1.1.9、Tencent Lemon 5.3.4；CleanMyMac CLI 作为 CleanMyMac 的命令行入口一并检查。
- 每个功能使用三层证据：本机界面与只读操作、同机扫描结果或能力输出、当前代码与测试/官方产品说明。
- 三轮顺序：第一轮建立基线并定位差异；第二轮修改后复测路径、风险和动作资格；第三轮做重复扫描、回归测试、签名安装与界面复核。
- 未执行实际清理、卸载、开机项切换、应用更新安装、风扇写入、电源模式写入或文件粉碎。
- 各软件扫描范围、容量口径和扫描时刻不同，容量只能帮助解释覆盖范围，不能直接当作优劣排名。

## 第二轮：修改与复测

### 已修改

1. 智能扫描长规则内部进度
   - 原因：百分比只使用“已完成规则数 / 总规则数”，最后一个大型根目录扫描时会长时间停在 93%。
   - 修改：Scanner 发布真实的当前顶层项目路径、已处理项数和总项数；共享 `DiskScanProgress` 将规则内真实进度纳入百分比。
   - 边界：显示的是当前规则直接候选的真实处理比例，不伪造深层文件级精确 ETA。

2. 应用更新汇总计数
   - 原因：本机显示“已检查 626 个应用”，六个操作分类合计 320；其余为 macOS/App Store 系统管理项目，但界面没有解释。
   - 修改：汇总页明确显示系统管理项目数量，并说明它们计入已检查总数但不会加入应用内批量更新。

### 第二轮证据

- 路径/规则/风险/动作资格哈希与第一轮完全一致。
- 候选仍为 82 个；容量从 185199837184 变为 185193123840 字节，属于活跃缓存的实时变化。

- 进度与应用更新汇总相关 5 个测试全部通过。

## 明确不复制的竞品行为

- 不把通用缓存、日志、微信/浏览器/Profile 数据默认勾选。
- 不处理当前运行应用的更新暂存文件。
- 不直接修改 Apple Mail 数据库、浏览器历史数据库或云端账号数据。
- 不剥离已签名应用的架构或语言资源。
- 不把文件粉碎、恶意软件防护、云端清理做成没有真实底层能力的装饰按钮。
- 不把测试、Mock 或协议通过描述成所有 Mac 的真实风扇/电源写入通过。

## 追加审计：嵌套应用与外部管理器移交

这组检查补充功能 #11，最新证据优先于上方较早的 Beta Build 记录。

### 第一轮：差距复现

- 安装版卸载器原来只读取 `/Applications` 与 `~/Applications` 的第一层，显示 86 个应用、约 82.1 GB。
- `/Applications/Setapp/AlDente Pro.app` 实际存在，但搜索 `AlDente` 没有结果。
- 根因一：卸载器维护了独立的浅层目录读取，没有复用应用更新的递归 `DirectoryApplicationScanner`。
- 根因二：即使模型发现外部管理应用，页面仍在 Presenter 前用 `canMoveToTrash` 过滤，安全禁用直接卸载的项目也因此被隐藏。

### 第二轮：底层修正与安全复核

- 卸载器改为复用统一应用目录扫描器，并将包式 `/Applications/Setapp` 集合作为同一扫描器的显式根目录；没有创建第二套扫描器、Store 或监控服务。
- 用户主动扫描使用最多 4 路并发，按应用名称公平调度，避免嵌套集合在 30 秒总时限下被父路径排序饿死。
- Setapp 应用被标记为外部管理：`canMoveToTrash == false`，推荐等级为 protected，只能打开 Bundle ID `com.setapp.DesktopClient` 对应的 Setapp。
- 显示层改为呈现“可直接卸载或可交给外部管理器处理”的应用；普通不可操作受保护项仍不进入主列表。
- 本机显式 Setapp 只读测试在 0.609 秒内读取集合并确认 AlDente；默认完整应用清单测试在 6.376 秒内同样确认 AlDente。

## 文件分析空间地图层级交互复核

- 本机 Tencent Lemon 5.3.4 的“磁盘空间分析”完成全盘扫描后，界面同时显示当前目录子项、同层级比例地图和面包屑路径。实机从 `Macintosh HD → Users → yyh → Library → Caches` 连续点击，目录块始终在应用内下钻，没有把主点击动作交给 Finder。
- StorageCleanerMac 原实现只把大型文件结果绘制成前 12 项地图，整个区块点击直接调用 Finder，无法继续理解目录内部结构。
- 现改为“扫描结果 → 子目录”的多层导航：目录行与目录块都触发同一个按需分析操作；文件点击只选中项目；返回、面包屑和已分析目录缓存保持同步；Finder 仅保留在独立按钮和上下文菜单中。
- 第二轮实机对照发现，虽然交互已经能下钻，但旧页面仍把容量汇总、类型分布、地图和普通大文件列表纵向堆叠，右侧地图会被外层滚动区裁掉下半部分，造成最大方块像是占满整个区域的错误观感。现改为专用分析工作区：顶部紧凑结果栏和“空间地图 / 文件列表”切换，下面固定为左侧同层目录列表、右侧完整比例地图；普通文件列表不再与地图同时争抢首屏。
- 右侧方块现在同时显示容量和父目录基准占比，间距降为 2 点。第三次实机复核发现，父目录“好玩的”为 3.8 GB，而限时子层扫描只量到至少 358.1 MB；若只拿已量到的小计作分母，150.2 MB 会被错误放大成 42%。现将父目录已知容量传入子层快照：未单独绘制但已测量的项目合并为“其他已测项目”，尚未量到的约 3.4 GB 保留为灰色“尚未完成测量”区域，150.2 MB 的面积回到约 4%。回归测试直接锁定这组本机权重和父目录基准。
- 下钻复用现有 `LargeFilesStore`、`DiskScanner` 与 `HeavyWorkCoordinator`。底层保持一次串行、低功耗的限时任务，并按“剩余时间 ÷ 剩余直接子目录”动态分配扫描预算；这样大型首项不会独占 8 秒预算，后续地图块也能获得真实的下限测量。返回已分析层级直接读取缓存，不会再次访问磁盘。
- 仍保持诚实边界：初始入口来自现有大型文件扫描，而非 Tencent Lemon 的全盘索引；超时、权限、扫描排除项、符号链接或未下载云端项目会使结果降级为下限，并在界面显示“至少占用”。
- 最终安装版已按竞品的信息结构复核：顶部为当前路径和返回控制，左侧为同层子项及独立 Finder 操作，右侧为同一数据源的比例地图；连续两层目录主点击都只在应用内更新列表、地图和面包屑。
