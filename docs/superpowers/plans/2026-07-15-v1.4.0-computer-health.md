# Storage Cleaner Mac v1.4.0 Computer Health Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a useful, low-overhead computer-health center with disk state, capacity trend, backup protection, stability, battery guidance and a cancellable manual network quality test.

**Architecture:** A root-owned `ComputerHealthStore` publishes bounded cached snapshots assembled from independent services; `NetworkSpeedTestStore` owns the only traffic-producing task. Services parse plist/JSON or bounded local metadata off MainActor, expose explicit availability states, and produce a lightweight `MenuBarHealthSummary` consumed by the menu without triggering work.

**Tech Stack:** Swift 6, SwiftUI, Foundation, Process, IOPowerSources/system_profiler, diskutil, tmutil, networkQuality, XCTest.

**Test fixture convention:** Every synthetic value or helper named in a test snippet (including `SequencedHealthProbe`, `.fixture`, `.oldFixture`, `.newFixture`, and `.reports`) is implemented privately in that test target as part of the task. Production services never read real user identifiers during fixture tests.

```swift
enum HealthStatus: String, Codable, Sendable {
    case healthy, attention, actionRequired, unavailable
}

enum HealthAvailability: String, Codable, Sendable {

struct ComputerHealthSnapshot: Sendable {

    let disk: DiskHealthSnapshot
    let capacity: CapacityTrendSnapshot
    let backup: TimeMachineSnapshot
    let stability: StabilitySummary
    let battery: BatteryHealthSnapshot?
}

struct MenuBarHealthSummary: Equatable, Sendable {
    let generatedAt: Date
    let diskStatusText: String?
    let capacitySevenDayDeltaBytes: Int64?

    let batteryCapacityPercent: Int?
    let batteryCycleCount: Int?
    let lastDownloadMbps: Double?
    let lastUploadMbps: Double?
    let lastSpeedTestAt: Date?
}
```

`ComputerHealthStore` uses a generation UUID and one physical refresh task. TTL refreshes reuse current data; forced refresh cancels or supersedes the UI generation without letting late results overwrite current state.
