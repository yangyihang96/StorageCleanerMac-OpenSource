## 4. 关键根因与修正

### 4.1 柱状图中间空档、当前数字与最新柱不一致

原实现有三个相互叠加的问题：

1. `GeekChartWindow.barMarks` 逐样本计算持续滚动相位，再用相同 x 的最后一个样本覆盖；它不是一个显式的“固定时间桶快照”。不规则采样、View 重建和跨 bucket 边界时，数据索引与可见槽位容易产生跳变或空档。
2. 标题/图例可以回退到实时 Provider，而柱图读取 History Store；两条数据路径更新时间不一致时，数字已经刷新但最右柱仍是旧历史。
3. 百分比指标曾允许按当前窗口局部范围缩放。最明确的例子是旧电池 `chargeRange(values:)`：按可见 min/max 加 padding，最小只保留 20% span；很小的真实变化会被放大成“高频锯齿/完美斜坡”。

修正后：

- `PanelChartTimeAnchor` 使用单调时间派生的统一 wall-clock reference；每张可见图使用同一 reference。
- `GeekChartWindow.barBucketSnapshots` 按 timestamp 进入固定槽位，最新值、tooltip 和 x 坐标复用同一 bucket snapshot。
- CPU 图例优先读取 `geekChartHistory.last.cpuUser/cpuSystem`，因此 22% + 12% 的图例和最右堆叠柱来自同一 telemetry point；测试断言总高度为 34%。
- CPU、Battery、Memory percentage、Pressure、Fan percentage 固定 0…100；Network/Disk 使用类型化 dynamic domain，扩张立即、下降按 tier 缓慢回落，baseline 不移动。
- 柱宽保持 2 pt、间距 1 pt、pitch 3 pt，没有用“更细的柱”掩盖数据错误。

### 4.2 电池斜坡、锯齿与电源时间线错位

- 审计确认旧电量图存在局部自动缩放；当前生产代码没有用随机波形生成 Release 历史，也没有根据预计充满时间生成未来趋势。
- 当前电池桶聚合规则是“该桶最后一个真实有效 `levelPercent`”；允许 `73,73,73,74,74,75` 这种平台/台阶。没有有效值时返回 nil，不画柱、不填 0，也不线性插值。
- 电池柱与 `PowerConnectionTimeline` 现在使用同一组 `GeekChartBucketSnapshot`：同一 `visibleStart/visibleEnd`、同一 plot、同一 x、同一 clipping。插电时粉色→蓝色与蓝线起点同 x；拔电时蓝色→粉色与蓝线终点同 x。
- 颜色来自共享 palette：电池供电粉色，外接电源和时间线蓝色，健康度洋红粉色，unknown 中性/不绘制；93% 健康度不再使用报警红。

### 4.3 小窗内存清理确认后无法完成

真实根因位于三个 Alert 表面的 Binding setter：SwiftUI 在执行 alert action/关闭展示时会写入 `false`，旧 setter 将这个被动展示写入解释成“取消计划”。当用户同时点击确认时，cancel 与 confirm 争用同一个 pending plan，导致操作停在确认后或直接失效。

修正集中在现有表面：Binding setter 不再改变操作意图；只有“取消”按钮调用 `cancelQuitSelectedMemoryProcesses()`，只有“正常退出/退出所选应用”调用 `confirmQuitSelectedMemoryProcesses()`。执行状态仍由应用级 `ScanStore`/Memory coordinator 持有，小窗关闭不会创建第二套 coordinator。

本轮没有为了演示而退出用户正在使用的应用，因此“真实应用正常退出 → 测量 → completed”仍列为未验证；定向测试已覆盖被动 dismissal 不取消计划、状态机和 coordinator 行为。

### 4.4 能耗为 0 的真实运行回归

为了遵守“禁止 `sh -c`”，进程枚举曾改为共享 `Shell.capture("/bin/ps", args)`。真实机器测试显示共享 runner 会在 `Shell.swift:962` 抛出 `terminationFailed("/bin/ps -axo ...")`；调用处使用 `try?`，错误被吞掉后形成空进程列表，UI 只显示 0 应用/0 功率。

修正为一个用途受限的 Foundation `Process` runner：可执行文件固定 `/bin/ps`，参数是固定数组，stdout/stderr 写临时文件，3 秒超时，失败返回空快照但不执行任意 shell。修复后真实 opt-in 测试 1/1 通过；能耗页读到约 40 个应用和 238–244 个进程。

### 4.5 整机 kWh 的数据来源和计算

`SystemEnergyAccumulator` 至少记录 monotonic timestamp、wall clock、watts、AC/battery/unknown、confidence、source 和 boot identifier；boot identity 优先来自公开 `sysctlbyname("kern.boottime")`。

积分规则：

```text
E_Wh += ((P_previous + P_current) / 2) × Δt / 3600
E_kWh = E_Wh / 1000
```

- 只有 `0 < Δt <= 90s` 且上一样本有效、供电来源已知时积分。
- AC/电池切换时，区间归属上一供电来源，避免切换点重复计算。
- missing、大间隔、应用退出间隔、sleep/wake 都会清空 last sample，不跨空档外推。
- AC 和 battery 分别累计；总量只做两者相加；累计值不可倒退。
- JSON 原子持久化到 `~/Library/Application Support/StorageCleanerMac/SystemEnergySession-v1.json`；actor writer 拒绝旧 snapshot 覆盖新值。
- 电池供电时，若公开电池电压/电流可用，使用原生测量并标为 `measured`；macOS 没有通用公开 AC 墙上功率计，因此 AC 使用现有可归属进程采样的估算并标为 `estimated / attributed-process-estimate`。
- 如果不是从 boot 时开始监测，UI 显示“估算”和覆盖率，不声称是 100% 精确电表读数。

### 4.7 重复文件确认与 APFS 边界

- 候选先按逻辑大小分组。
- 快速比较读取头 64 KiB 和尾 64 KiB。
- 快速指纹一致后，以 1 MiB chunk 流式计算完整 SHA-256。
- `device + inode` 去重，硬链接不会重复计入可释放空间。
- `O_NOFOLLOW`、lstat/fstat、size/mtime/ctime 前后复核；扫描中变化、不可读、消失的候选 fail closed。
- 符号链接、package、隐藏/受保护目录、CloudStorage、node_modules、.git 等默认跳过。
- 公共 API 无法从“逻辑内容相同”可靠推导 APFS clone/block sharing，`estimatedPhysicalReclaimableBytes` 因此保持 nil；界面只声明逻辑重复大小，物理可释放空间写“待验证”。
- 清理确认已由只显示数量的 alert 改为原生 sheet：直接投影冻结的 Clean Plan 与 Preflight，只列出 `.ready` 项，并逐组显示“保留”路径和“将移入废纸篓/隔离区”路径；跳过项只计数，不会混入移动列表。
- 实际删除仍必须回到既有 Trash/Quarantine 与恢复链。本轮没有执行真实删除。
