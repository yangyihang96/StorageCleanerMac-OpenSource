## 2. 改了什么

- **编排**（新文件 `Models/SmartCareModule.swift`、`Stores/SmartCareLiveScanner.swift`）：
  - `SmartCareModule`（5 个模块，选择单独保存在 `smart-care.selected-modules`，默认全选）、`SmartCareCardState`。
  - `SmartCareCoordinator`：每个 store 一个，5 个模块依次扫描，带“停止”和“重新开始”。
  - `LiveSmartCareScanner`：各模块都调自己现成的入口；只在智能扫描进行时，每 0.2 秒查一次该模块公开的状态。
  - 顺序和租约：
    1. 清理：垃圾扫描，`.mainScan`。始终扫两项文件范围、不做健康检查，照旧写历史。
    2. 防护：浏览记录，不占租约。
    3. 性能：登录项＋维护任务探测，不占租约。
    4. 应用：查更新，`.appUpdates`，会联网。没网时标“没有网络连接”，不去查。
    5. 杂乱：重复文件，`.duplicateScan`。
  - 某一步拿不到租约（别的任务在跑），就标“另一项任务正在进行”，接着做下一步。
- **ScanStore**：
  - 新增 `prepareSmartCareCleanupScopes()`（清理卡开始前把范围设为两项文件范围）和 `smartCarePreferences`。
  - `refreshAppUpdates()` 对外不变，开头仍是 D106 的验收模式守卫；检查主体挪进 `runAppUpdateCheck(resumesSavedQueue:)`。
  - 新增 `checkAppUpdatesForSmartCare()`：第一句同样是 D106 守卫，以 `resumesSavedQueue: false` 检查——不续保存的更新队列（`restoreApplicationUpdateQueueIfNeeded`）、不续网站更新助手、不评估静默更新。应用更新页自己的检查三样照旧。
- **可用更新数**：挪成 `ScanStore.availableAppUpdateCount`，应用结果页和智能扫描的应用卡读同一个数。
- **起始页**：三项范围换成 5 个模块开关，每行写明扫什么，应用一行注明“会联网查询”；至少开一项才能扫描，“扫描”交给 Smart Care。副标题和侧栏悬停说明去掉了健康，改成 5 个模块。
- **扫描中**（新文件 `CareStudio/CareStudioSmartCare.swift`，`SmartCareScanningPage`）：
  - 运行页下面一排 5 张小卡，每张有模块图、名称和状态（等待中 / 正在扫描… / 找到的数 / 跳过原因 / 失败 / 已停止）。
  - “停止”先问一句（“已扫描完的模块保留结果，其余的不再扫描”），然后停当前模块，其余标“已停止”，进入结果页。
- **结果页**（`SmartCareResultsPage`）：
  - 标题，下面是 bento 布局的 5 张卡：清理是左边的大卡，其余 4 张在右边 2×2。每张卡的数值和说明从模块的实时数据现算。
  - 清理卡在有勾选的垃圾时显示勾选框，决定“运行”是否清理它。
  - “查看”的去向：
    - 清理：在这里打开垃圾管理器，只改选择，返回后仍是 5 张卡；
    - 性能：有建议的维护任务时打开维护任务，否则打开登录项；
    - 防护：浏览记录；应用：应用更新；杂乱：重复文件。
  - 圆按钮“运行”：清理勾选的垃圾，走原有的清理计划和所有确认。第三批 L 再加维护任务。
  - 左上角“重新开始”。
- **流转宿主**（`ContentView` 的 `SmartScanFlowHost`）：
  - 只在智能扫描页显示这两页。确认时 5 张卡留在确认单下面；清理中、核对中和完成页仍用原来的；完成后点“完成”，清掉 5 张卡、回到起始页。
  - 别的页借用这个宿主做清理时，仍走原来的垃圾流程，即使智能扫描正在扫或停在结果页。
- **都没变**：垃圾扫描的风险分级、预选、确认、执行和恢复；历史和菜单栏、小窗的垃圾数字；各模块自己的页面和操作；经典（D70）起始页；`SmartScanScope` 和健康阶段的代码（旧记录仍能读，只是智能扫描不再请求健康）。
