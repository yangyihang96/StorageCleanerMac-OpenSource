### 本轮读取、结果和权限文案收口

- 之前的覆盖摘要把 `partial` 与 `available` 一并显示为“已读取”，会把只读到部分 profile 的浏览器误报为完整读取；现在摘要分别显示“完整读取 / 部分读取”，并单独计数需要“完全磁盘访问权限”的浏览器。
- Provider/SQLite 层现在保留 `requiresFullDiskAccess` 证据。profile 目录、history/places 数据库文件和子目录的权限错误都会沿发现链路保留；Foundation 通过 `NSPOSIXErrorDomain` 返回 `EACCES` 或 `EPERM` 时，也按权限缺失处理，不再降级为“没有 profile”或笼统“不可用”。
- 结果页会显示具体浏览器覆盖卡片、缺失权限原因和“下一步：检查系统设置授权”，并提供“检查授权”按钮打开系统设置；该按钮只打开设置，不会打开历史 URL、写入数据库或删除记录。
- 定向验证：`BrowserPrivacyRecordScannerTests` 9/9、`PrivacyCleanupPresentationTests` 19/19；Debug 与 Release build 均 exit 0。上述结果只证明 fixture/代码路径，不代表本机已授予 Full Disk Access 或完成真实浏览器读取。

## 5. 删除能力边界

生产边界是 **全部 Provider 只读、全部处理走浏览器内手动流程**。12 个静态注册 Provider 与动态发现 Provider 的 `historyWriteAdapter` 均为 `nil`；扫描不会生成生产写 locator，结果页不会调用数据库处理入口。

`BrowserPrivacySQLiteWriteAdapter`、`BrowserPrivacyHistoryProcessor` 和可写 SQLite fixture 仍保留在源码与测试中，用于验证历史设计的事务、回滚和身份边界，但当前产品 Registry 不授予它们生产可达性。这些 fixture 结果不能当作真实浏览器删除证据。

用户选择记录后，`prepareManualGuidance()` 生成可操作的四步流程：

1. 查看或复制去重后的所选域名；
2. Chromium 只打开固定 `chrome://history/`，Safari/Firefox 显示其历史菜单路径，由用户在浏览器内处理；
3. 处理完成后由用户正常退出相关浏览器；本应用不强制退出；
4. 浏览器完全退出后重新执行只读扫描，以新的读取结果确认记录是否仍存在。

该流程不会修改浏览器数据库，也不会自动删除历史记录、Cookie、密码、书签或自动填充。重新扫描只是只读验证，不把“已打开步骤”或“用户点击完成”记录成清理成功。

## 12. Chrome 150 多表写入前置审计（2026-08-04）

- 本机 Google Chrome `150.0.7871.187` 的 Default `History` 仅通过临时只读副本核对；副本以 `mode=ro&immutable=1` 打开且 `quick_check=ok`，未输出 URL、标题、搜索词或注释内容，真实数据库前后 size/mtime/ctime 未变化。
- 当前 schema 为 `meta.version=70`、`last_compatible_version=16`，全库没有显式 foreign key 或 trigger。`urls`、`visits`、`visit_source`、`segments`、`segment_usage`、`context_annotations`、`content_annotations` 均存在，但真实依赖还包括 `clusters_and_visits`、`cluster_visit_duplicates`、`keyword_search_terms` 和 `visited_links`。
- `urls.visit_count` 由 Chromium 应用层维护，本机已有合法记录与当前 `visits` 聚合数不相等；因此不得用 `COUNT(visits)` 覆盖回写。Chromium 当前官方删除流程会修补 `visits.from_visit`，删除 visit/source/annotations，并按 transition 与 `incremented_omnibox_typed_score` 分别递减 URL visit/typed counts，再用剩余真实访问更新 `last_visit_time`。
- 结论：现有单表 fixture adapter 仍不能升级为生产授权。下一步只允许在带临时目录 marker 的隔离 fixture 中建立 deny-by-default 多表事务、提交前 invariant 与提交后只读复核；所有生产 Provider 继续 `historyWriteAdapter == nil`，真实 Chrome 数据库继续零写入。
- 隔离实现现已加入 `chromiumV70Fixture`：运行时同时要求数据库位于当前用户临时目录、同目录 marker 内容/所有者/权限/长度精确匹配，并要求七张关联表与 `meta.version=70` 的 fixture 列集合精确匹配。写 authorizer 默认拒绝，仅放行 source/两类 annotation/visit 的 DELETE、`visits.from_visit` 和三个 URL 派生字段的 UPDATE；INSERT、DDL、ATTACH、未声明表和未声明列全部拒绝。
- fixture partial-delete 会在同一 `BEGIN IMMEDIATE` 中修补 `from_visit`、删除 visit 关联行、按 Chromium 官方语义递减 visit/typed counts，并从剩余真实 visit 取得 `last_visit_time`；不删除 URL、segment 或 segment usage。最后一条 visit、非零 `visited_link_id`、已知额外依赖、非完整 redirect parent 集合或 schema/marker 不匹配均 fail closed。
- `BrowserPrivacyHistoryProcessorTests` 当前 **21/21 通过**：包括多表 happy path、segment/usage 保持、最后 visit 拒绝、marker 缺失、越界 authorizer 拒绝，以及在前序多表 DELETE 完成后由 URL `CHECK` 触发失败并证明八张表全部回滚。该结果仍只属于临时 fixture；生产 Provider 继续全部返回 `nil`，未写入真实 Chrome 数据库。
