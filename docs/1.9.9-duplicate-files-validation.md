## 2. 当前扫描范围

界面现在明确提供两个范围：

- “用户文件”：合并常用用户目录、自定义目录和用户明确选择的外接卷；
- “用户数据区”：覆盖可读用户数据区、自动发现的本地且可浏览 `/Volumes/...` 数据卷，以及用户明确选择的卷。不会从系统盘根目录 `/` 盲扫。内部兼容枚举/API 名称仍为 `.wholeComputer`。

`DuplicateFileScanner.Configuration.userFiles` 默认合并：

- Downloads；
- Desktop；
- Documents；
- Movies；
- Music；
- Pictures；
- 用户添加的自定义目录；
- 用户明确添加的外接卷根目录。

自动卷发现只接受本地、可浏览的数据卷；排除根卷、系统/受保护卷、网络卷、不可浏览卷、只读的内部系统容器和无效 URL。用户明确选择的卷仍保留，不会被自动发现结果覆盖。嵌套根会去重。

每个纳入扫描的卷都生成同一组受保护子路径：`Applications`、`System`、`Library`、`private`、`usr`、`bin`、`sbin`、`opt` 和 `cores`。因此即使外接卷包含可启动系统，也不会进入其系统目录。

两套生产配置的 `minimumBytes` 均为 **0**，因此会检查所有达到其他边界条件的常规文件；隐藏文件不会枚举，单目录读取时限均为 0.5 秒。系统保护目录、应用包、缓存挂载、伪文件系统和 Time Machine 位置明确跳过。其余边界明确分开：

| 用户可见范围 | 内部配置 | 实际根目录 | 文件上限 | 目录上限 | 深度上限 | 结果上限 | 总时限 |
|---|---|---|---:|---:|---:|---:|---:|
| 用户文件 | `.userFiles` | 常用用户目录 + 自定义目录 + 明确选择的外接卷 | 8,000 | 900 | 5 | 120 | 10 秒 |
| 用户数据区 | `.wholeComputer` | 可读用户数据区 + 自动发现的本地可浏览数据卷 + 明确选择的卷 | 250,000 | 30,000 | 12 | 200 | 30 秒 |

因此，两种范围都是 **有界扫描**；“用户数据区”不表示无条件扫描整台电脑、所有卷或所有文件。达到任一上限时报告必须是 `partial` 并列出 coverage 原因；覆盖报告同时显示实际根目录和跳过原因。

2026-08-03 本机只读枚举中，`FileManager.mountedVolumeURLs` 只返回 `/`。根卷按策略排除后没有自动外接数据卷可供扫描；自动卷纳入行为目前只有 fixture 证据。

## 4. 文件身份与覆盖安全

当前代码合同包括：

- `device + inode` 去重，硬链接不作为两份重复内容计数；
- `O_NOFOLLOW` 打开候选，符号链接不跟随；
- 读取前后复核 size、mtime、ctime 和 inode，扫描中发生变化即 fail closed；
- 不可读、消失、超时、权限拒绝、package、伪文件系统、Time Machine 和策略排除都有明确 skip reason；
- 可暂停、恢复和取消；进度报告当前路径、扫描/哈希文件数和字节数；
- exact 与 candidate 分开显示，搜索命中组内一个成员时保留整组；
- 过滤、排序、自定义/外接范围持久化，但破坏性选择不跨重启恢复。

未完成扫描会在完整目录边界写入恢复索引：最多 32 MB、24 小时有效，目录权限 0700、文件权限 0600、原子替换；恢复前复核配置、根路径、候选路径与数量，并拒绝符号链接、非当前用户所有或硬链接索引。发现阶段取消后可从最近目录边界继续；哈希阶段中断会复用已确认的发现索引重新哈希，不复用未经复核的 digest。

## 5. 删除安全链

`DuplicateFilesStore` 和 `VerifiedDuplicateRequestFactory` 在进入既有安全清理前执行：

1. 只接受当前仍 available 的完整 SHA-256 exact 项；
2. 每组至少保留一个未选择副本；
3. 再次读取选中项和保留项快照；
4. 当前应用内移动目标限制在用户 Home；外接卷结果只供审阅；
5. 生成带 digest、期望快照和保留副本证据的 verified request；
6. 原生确认 sheet 从冻结的 Clean Plan 与 Preflight 投影逐组路径，只把 `.ready` 项列入“将移入废纸篓/隔离区”，并明确列出至少一份保留副本；跳过项只显示数量；
7. 后续仍须经过明确确认 → Trash/Quarantine → 执行时身份复核 → 报告/恢复。

本轮没有执行第 7 步的真实文件移动，也没有验证恢复。

## 6. APFS 物理空间边界

完整 SHA-256 相同的文件会额外通过公开 AppleArchive `CLC`/`HLC` 字段分类为独立数据、APFS clone、硬链接或未知关系。`device + inode` 硬链接仍在发现阶段去重；CLC 只证明 clone 簇关系，不能证明删除后实际释放多少 block，因此 `estimatedPhysicalReclaimableBytes` 始终为 `nil`，APFS clone 界面显示“物理释放空间待删除后确认”。普通副本不会因大小或逻辑内容相同被误判为 clone；AppleArchive 读取失败时保持 unknown。

## 18. build 202608050837 APFS clone 关系分类与诚实空间语义

- 完整 SHA-256 相同的文件现在额外使用系统公开 AppleArchive path-list metadata 读取 `CLC` / `HLC`，分类为 `independent`、`apfsClone`、`hardLink` 或 `unknown`。该探测不读取私有 APFS extent、不联网，也不使用文件大小、`st_blocks` 或 allocated size 猜测共享物理块。
- 既有 `device + inode` 硬链接去重保持不变。AppleArchive 读取失败、路径身份变化或证据不完整时统一 fail closed 为 `unknown`；普通独立副本没有 CLC/HLC 时显示独立数据，真实 `clonefile` 临时 fixture 由相同 CLC 确认 `apfsClone`。
- APFS clone 只证明两个路径属于同一 clone 簇，不证明删除其中一个会释放多少卷空间。`estimatedPhysicalReclaimableBytes` 继续为 `nil`，界面显示“物理释放空间待删除后确认”；移到 Trash/Quarantine 也不等于物理空间已释放。
